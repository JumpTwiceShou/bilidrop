# 无人值守挂机与桌面运行时重构

## 背景

当前桌面程序已经支持多账号、任务识别、观看心跳与奖励领取，但仍存在重复启动、关闭行为不符合桌面常驻程序习惯、无任务时不能低成本等待、任务开始时间未参与调度、并发数只能固定，以及奖励领取重复请求和状态误判等问题。

## 本次范围

- Windows 单实例：第二次启动不创建新实例，改为唤醒并显示已运行窗口。
- 系统托盘：最小化和关闭默认收进托盘；高级设置允许分别关闭这两个行为；托盘提供显示、启动、停止、退出。
- 自动挂机：
  - 启用后在没有可执行任务时继续后台发现。
  - 普通等待间隔 15 分钟。
  - 已识别到未来任务且尚未到开始时间时，等待间隔降为 60 分钟，并在临近开始时间精确唤醒。
  - 到达开始时间或检测到直播间开播且存在可执行任务时自动启动观看心跳。
  - 当天任务全部完成后停止观看心跳，但继续发现后续任务。
  - 任务开始、结束时间进入任务模型和界面状态。
- 主界面运行控制：
  - 当前账号“开始 / 停止”。
  - 所有账号“全部开始 / 全部停止”。
  - 全局“后台自动挂机 / 停止后台自动挂机”。
  - 三组控制平铺显示；用简短小字解释后台自动挂机的轮询、开播启动、完成停心跳和继续守候行为。
- 心跳并发：
  - 保留固定并发模式。
  - 新增自动并发模式；落后时以最多 32 个会话追赶。
  - 基于连续进度样本计算“任务进度 / 墙钟时间”速率；确认已接近正常实时增长后降至 2 个会话。
  - 使用采样窗口、容差、冷却与上下限，避免进程数频繁抖动。
- 奖励领取：
  - 同账号同任务领取互斥，阻止自动领取、刷新和手动领取并发重入。
  - 外层任务与奖励节点去重，正确携带并兼容解析 `award_outer_id`。
  - 已领取状态本地合并并由后续服务端状态确认，不再长期显示“自动领取中”。
  - 限频采用退避和冷却，缺少必要字段时停止无效重试并输出可理解原因。
- 验证：
  - 读取用户指定 Codex 会话中的进度加速观察。
  - 使用用户指定 Chrome 插件只读检查真实任务页的时间字段与领奖显示。
  - 补充聚焦单元测试与桌面运行时测试。
  - 构建新的单文件 Windows 可执行程序，不覆盖或中断当前正在运行的旧实例。

## 明确不做

- 不在验证时真实领取奖励。
- 不读取 Chrome Cookie、密码、Local Storage 或其他敏感浏览器存储。
- 不停止用户当前正在运行的挂机程序。
- 不提交、推送或公开发布。

## 验收标准

- 连续启动两次时只有一个主实例，第二次启动让已有窗口恢复并置前。
- 默认点击最小化或关闭后仍驻留托盘，设置关闭后恢复普通行为；显式“退出”能结束进程。
- 开启自动挂机后，无任务时程序不发送观看心跳；能按 15/60 分钟策略继续发现并在任务可执行时启动。
- 主界面可分别控制当前账号、全部账号和全局后台自动挂机；批量操作不会重复启动已运行账号，也不会因一个账号失败阻塞其他账号。
- 当前任务完成后心跳停止，调度器仍保持活动。
- 设置中可选固定或自动并发；自动模式有可测试的 32→2 状态转换，不依赖 UI 阻塞。
- 刷新/自动领取/手动领取同时触发时，同一任务最多存在一个领取请求链。
- 已领取节点刷新后显示已领取；缺少 `award_outer_id` 不再进入高频循环；限频后进入明确冷却。
- 相关测试通过，并产出不与运行中旧文件冲突的新单文件 EXE。

## 关键决策

- `totalv2` 的奖励节点状态按真实页面/API 解释：`2=已完成可领取`，
  `3=已领取`，同时只为旧缓存兼容 `6=已领取`。
- 领奖查询和提交使用奖励节点 `sid`；外层任务 ID 只用于查询当天整个任务系列。
- 自动领奖失败按 60 秒、5 分钟、15 分钟、1 小时逐级冷却。
- 自动挂机当前任务每 15 分钟复查；未来任务每 1 小时复查并在开始时间提前
  唤醒。最终节点先经过账号领奖互斥链确认，再停止心跳。
- 自动并发未知或已开始一段时间时用 32 个会话；连续样本确认进度约为
  1 倍真实时间后降为 2 个会话。
- “当前账号”“所有账号”“无人值守”作为三组并排控制；每组保留明确的
  开始与停止按钮，下面用小字说明自动挂机行为。
