# BiliDrop 运行逻辑架构优化方案

## 1. 目标与结论

当前最需要解决的不是单个按钮或单个接口，而是“同一账号存在多套状态来源”：

- `MinerGUI` 保存界面与账号工作区状态；
- `WorkerController` 保存线程和 Miner 状态；
- `AccountTaskMonitor` 保存任务、领奖与通知状态；
- 后台自动挂机又单独保存守候、检查和运行归属状态。

这些状态通过布尔值、集合和回调互相推断，造成加载设置、切换账号、任务完成、手动/自动混用时容易出现状态不一致。

目标架构是：

1. 每个账号只有一个 `AccountAgent` 作为运行状态和网络操作的唯一入口。
2. 手动启动与后台自动启动使用同一运行命令，但必须携带明确的启动原因和运行所有者。
3. 任务查询、领奖和通知使用统一任务快照与统一领奖服务。
4. 全局默认设置、账号覆盖设置和仅本次覆盖设置分层保存，禁止互相覆盖。
5. Qt 主窗口只展示状态和发送命令，不直接管理线程、API 请求或业务状态。

本方案采用渐进替换，不一次性推倒重写。

## 2. 当前问题与风险

| 优先级 | 当前问题 | 用户可见影响 | 根因 |
| --- | --- | --- | --- |
| P0 | 领奖异常路径可能再次抛出未初始化变量错误 | 真正的领奖失败原因被掩盖，界面可能一直等待 | `TaskController.claim_rewards()` 的 `refresh_after` 未在 `try` 前初始化 |
| P0 | 加载设置只清除后台自动集合 | 界面显示后台自动已关闭，但自动启动的心跳仍可能继续 | UI 状态与运行状态没有统一停止命令 |
| P0 | 自动完成、未来任务等分支可能停止手动运行 | 用户手动开始的挂机被后台逻辑误停 | 运行只有 `auto_started_runtime` 布尔值，停止分支没有统一校验所有者 |
| P1 | 一个账号有多条 API 调用路径 | 刷新、识别、领奖互相抢占，容易触发限频或得到乱序结果 | GUI 线程、任务控制器和运行时监视器分别创建客户端和线程 |
| P1 | 设置作用域不明确 | 当前账号显示的设置、重新打开后的默认值、应用到所有账号的结果可能不同 | 全局设置和账号运行字段混在 `AccountWorkspace` 与单一设置对象中 |
| P1 | 临时账号跳过启动前登录校验 | 失效 Cookie 可能以游客模式运行，用户误以为正在计时 | 临时/已保存身份被错误地用作是否校验登录态的条件 |
| P2 | 主窗口承担几乎所有业务 | 修改一个流程容易影响账号、托盘、任务、领奖或设置 | `main_window.py` 约 2800 行，缺少业务服务层和单向状态流 |

## 3. 必须建立的业务不变量

重构后的代码和测试必须始终满足以下规则：

1. 后台自动逻辑只能停止 `owner=AUTO` 的运行；手动运行只能由用户、退出程序或明确的“停止全部”停止。
2. 同一账号同一时刻最多有一个任务查询、一个任务识别和一个领奖操作；重复请求必须合并而不是并行发送。
3. 旧请求返回时，如果账号、房间或任务代次已经变化，结果必须丢弃。
4. 任务完成和奖励领取是两个状态：完成不等于已领取，领取中也不等于领取成功。
5. 后台自动挂机开关属于本次程序运行，默认不随程序启动恢复。
6. 仅本次并发覆盖不写入持久设置；持续模式必须明确写入账号设置或全局默认值。
7. 登录接口临时失败不能被记作 Cookie 永久失效；确认未登录才进入 `INVALID`。
8. UI 展示的运行状态必须来自账号状态快照，不能根据按钮文字或集合成员关系反推。

## 4. 目标状态模型

不要创建一个包含几十种组合的巨型枚举。将账号状态拆为四个互相独立但由同一状态中心管理的维度：

### 4.1 运行状态

```text
STOPPED -> STARTING -> RUNNING -> STOPPING -> STOPPED
                       \-> FAILED
```

### 4.2 运行所有者

```text
NONE | MANUAL | AUTO
```

- `MANUAL`：点击“开始”产生。
- `AUTO`：后台守候检测到任务并自动开始产生。
- 停止后台自动时，只向 `AUTO` 运行发送停止命令。

### 4.3 后台自动状态

```text
OFF
ARMED
CHECKING
WAITING_TASK
WAITING_LIVE
AUTO_RUNNING
CLAIMING
COOLDOWN
```

### 4.4 任务阶段

```text
UNKNOWN | FUTURE | ACTIVE | COMPLETED | EXPIRED
```

对应的数据对象建议如下：

```python
@dataclass(frozen=True, slots=True)
class AccountState:
    session_id: str
    runtime_state: RuntimeState
    run_owner: RunOwner
    automation_state: AutomationState
    task_phase: TaskPhase
    generation: int
    active_task_key: TaskKey | None
    next_check_at: float | None
    health: RuntimeHealth
    snapshot: TaskSnapshot
    last_error: OperationError | None
```

`generation` 每次更换 Cookie、房间或任务组时增加。后台结果携带发起时的 generation，返回不一致时直接忽略。

## 5. 每个账号一个命令入口

新增 `AccountAgent`，它不是新的 OS 线程，而是账号业务的协调对象：

```text
Qt UI
  -> AccountCommandBus
      -> AccountAgent
          -> RuntimeService
          -> TaskService
          -> DiscoveryService
          -> RewardService
          -> AccountRequestScheduler
  <- AccountState snapshot
```

建议命令：

- `ManualStart`
- `ManualStop`
- `EnableAutomation`
- `DisableAutomation`
- `RefreshTasks`
- `ClaimRewards`
- `RecognizeTasks`
- `ApplyConcurrencyOverride`
- `UpdateConfiguration`
- `Shutdown`

所有命令返回结构化结果，不直接弹窗。Qt 层根据错误代码决定提示内容。

## 6. 七项问题的具体优化方式

### 6.1 领奖路径统一

短期先修复 `refresh_after` 未初始化问题，并补异常测试。随后删除 GUI 的独立领奖实现，手动领奖与自动领奖都发送到 `RewardService`。

`RewardService` 应维护每个奖励节点的状态：

```text
NOT_READY
CLAIMABLE
CLAIMING
CLAIMED
RETRY_WAIT
FAILED
```

关键规则：

- 同一个 `RewardKey` 同时只允许一个领取请求。
- 手动领取遇到正在自动领取时，合并到同一个 Future，而不是提示后再开一条请求。
- API 返回成功或“此前已领取”后，先进入 `CLAIMED_PENDING_CONFIRMATION`，随后刷新任务状态确认。
- 查询仍显示可领取时，显示“待确认/稍后复查”，不能无限显示“自动领取中”。
- 重试使用统一退避：60 秒、5 分钟、15 分钟、1 小时；服务端明确限频时所有领奖请求共享冷却。
- 不再直接修改第三方 `TaskProgress.status`；使用本地不可变状态覆盖层生成 UI 快照。

### 6.2 加载设置与后台运行一致性

加载设置不能直接清空 `_automatic_mining_session_ids`。

改为以下流程：

1. 读取并校验新设置，但暂不修改运行状态。
2. 计算新旧设置差异。
3. 对正在运行的账号：
   - 仅 UI/托盘/更新设置可立即应用；
   - 房间、Cookie、重连、并发策略等运行参数标记为“下次启动生效”；
   - 如果用户明确要求关闭后台自动，发送 `DisableAutomation` 命令。
4. 等状态机确认自动运行已停止后，UI 才显示后台自动关闭。

设置加载必须是一次事务：成功则所有字段一起替换，失败则保持原状态。

### 6.3 手动/自动运行所有权

删除“根据某个分支猜测该不该停止”的逻辑，所有停止都通过：

```python
StopRuntime(reason, allowed_owners={RunOwner.AUTO})
```

行为矩阵：

| 场景 | MANUAL 运行 | AUTO 运行 |
| --- | --- | --- |
| 点击停止当前账号 | 停止 | 停止 |
| 点击停止全部 | 停止 | 停止 |
| 关闭后台自动 | 保持 | 停止 |
| 发现未来任务 | 保持 | 停止并等待 |
| 当天任务完成 | 保持，继续由用户控制 | 停止心跳、领取、继续守候 |
| 任务过期 | 保持并提示任务信息过期 | 停止并清除旧任务 |
| 退出程序 | 停止 | 停止 |

这样可以同时修复未来任务、任务完成、加载设置和关闭自动时的误停问题。

### 6.4 统一网络请求与限频

第一阶段不必立刻改成全应用单事件循环。可先为每个账号增加 `AccountRequestScheduler`，让现有线程和 Miner 都通过它发请求。

调度器职责：

- 任务刷新：多个刷新请求合并为一次，完成后如有新请求只再执行一次。
- 领奖：按奖励节点串行执行并共享冷却。
- 任务识别：同房间只保留最新 generation 的一次请求。
- 登录校验：短时间内复用上次结果，Cookie 变化立即失效缓存。
- 多账号：启动和查询增加抖动，避免所有账号在同一秒访问。
- 限频：识别 B 站限频结果后进入账号级冷却；UI 显示剩余冷却时间。

第二阶段再将后台工作统一到一个长期运行的 asyncio 服务线程，删除散落的 `threading.Thread + asyncio.run()`。

### 6.5 设置分层与迁移

配置应拆成三层：

```text
GlobalDefaults
  + AccountOverrides
      + RuntimeOverrides
          = EffectiveAccountConfig
```

建议字段归属：

| 层级 | 字段 |
| --- | --- |
| 全局默认 | 托盘行为、更新检查、日志、默认重连、默认查询间隔、默认并发策略、通知地址 |
| 账号覆盖 | 常用房间、固定/自动并发选择、固定并发数、是否通知、账号备注 |
| 运行时覆盖 | 当前任务 ID、当前任务时间、后台自动是否开启、仅本次 100、运行所有者、下一次检查时间 |

迁移到配置 schema v5：

1. 现有 `application-settings` 读取为全局默认值。
2. Cookie 和 credential ID 不变，不重新加密、不改变备注。
3. Cookie 档案元数据增加可选 `settings` 字段；没有该字段的账号继承全局默认值。
4. 任务 ID、任务进度和后台自动开关不持久化，避免第二天加载旧任务或开机自动挂机。
5. 写入前沿用现有加密存储备份；写入后重新读取并比对。
6. 迁移失败时继续使用旧结构，不能删除旧元数据。

### 6.6 登录态统一

临时账号和保存账号都必须经过相同验证，区别只在“是否持久化”。

登录状态应增加原因和时间：

```python
LoginStatus(state, checked_at, uid, error_kind)
```

规则：

- 二维码登录成功可立即标记为有效，并保存校验到的 UID。
- 手工粘贴 Cookie 在第一次启动前必须校验。
- 网络超时为 `ERROR_RETRYABLE`，不能标成 `INVALID`。
- 接口明确未登录才标成 `INVALID` 并阻止启动。
- 同 UID 重新扫码只更新 Cookie，保留备注和账号覆盖设置。
- 运行中的 Cookie 不热替换；新 Cookie 在下次启动生效。

### 6.7 拆分主窗口

最终文件边界建议：

```text
gui_parts/main_window.py              只负责窗口装配和 Qt 信号
gui_parts/account_presenter.py        账号下拉框、状态文本、按钮状态
gui_parts/task_presenter.py           任务表格和奖励状态
application/account_coordinator.py    账号命令与状态快照
application/automation_reducer.py     后台自动状态机（纯函数）
application/config_service.py         三层配置合并与迁移
services/account_agent.py             账号异步业务入口
services/request_scheduler.py         请求合并、限频和冷却
services/reward_service.py            唯一领奖实现
services/runtime_service.py           Miner 启停与并发调整
```

Qt 层不得直接引用 `BilibiliClient`、`threading.Thread` 或 `asyncio.run()`。

## 7. 自动并发在新架构中的位置

并发策略需要显式输入，不能再从任务时间或进度猜测启动来源：

```python
ConcurrencyStartContext(
    reason=MANUAL | AUTO_IMMEDIATE | AUTO_GUARDED,
    armed_seconds=...,
    task_key=...,
)
```

规则保持为：

- `MANUAL`：单账号 32、多账号每账号 16 开始，3 分钟后判断。
- `AUTO_IMMEDIATE`：单账号 32、多账号每账号 16 开始，3 分钟后判断。
- `AUTO_GUARDED`：2 开始。
- 仅本次 100 绑定当前运行；本次运行结束后自动失效。
- 持续固定 32 写入账号覆盖值；如果用户选择“所有账号”，逐账号写入。
- UI 同时显示策略、实际目标连接数、决策原因和下次判断时间。

## 9. 验收测试矩阵

### 9.1 状态机测试

- 手动启动后开启再关闭后台自动，手动运行保持。
- 自动启动后关闭后台自动，自动运行停止。
- 手动运行遇到未来、完成或过期任务，不被后台自动分支停止。
- 自动任务完成后停止心跳、领取奖励并继续守候。
- 房间或 Cookie 改变后，旧识别结果不能覆盖新状态。

### 9.2 请求调度测试

- 连续点击刷新十次只产生一次正在执行和最多一次排队刷新。
- 手动领取与自动领取同一奖励节点只发送一次请求。
- 限频后刷新/领奖遵守同一账号冷却。
- 多账号查询经过抖动，不在同一时间形成请求尖峰。

### 9.3 设置迁移测试

- v2 现有账号、备注、Cookie 和最近使用账号完整保留。
- 没有账号覆盖值时继承全局默认。
- 仅本次 100 和后台自动开关重启后消失。
- 持续固定模式重启后仍在正确账号生效。
- 迁移写入失败后原文件与元数据仍可读取。

### 9.4 登录与故障测试

- 临时手工 Cookie 未验证时不能启动。
- 网络错误显示“检测失败/可重试”，不误报“登录失效”。
- 同 UID 扫码更新 Cookie 不覆盖备注和账号设置。
- 关闭窗口到托盘不停止运行，退出程序会有界停止所有运行。

### 9.5 必要的人工验证

- 真实账号二维码登录与失效 Cookie。
- 当前活动房间的后台识别、开播检测与任务进度。
- 60/120/180 等节点自动领取和领取后状态确认。
- 两个账号同时挂机时的请求错峰与托盘恢复。
- 单账号自动 32、多账号自动 16、稳定 2 和仅本次 100 的实际连接数变化。

## 10. 可观测性与诊断

每个账号保留最近 200 条结构化事件，导出诊断时脱敏：

```text
timestamp
session_id（随机 ID，不含 Cookie）
command
old_state -> new_state
task_key（可哈希）
request_kind
cooldown_remaining
runtime_owner
concurrency_target / reason
error_code（不含响应中的敏感字段）
```

运行区建议显示：

- `手动运行 / 后台自动运行`
- `后台守候：下次检查还有 12 分钟`
- `单账号自动追赶 32 / 多账号自动追赶 16 / 自动稳定 2 / 本次固定 100`
- `领奖：可领取 / 领取中 / 待确认 / 已领取 / 冷却重试`

这样出现“不加速、没停、没领取”时可以直接判断是哪一层状态，而不是依赖长日志猜测。

## 11. 不建议的做法

- 不要直接把全部 GUI 和运行时代码一次性重写。
- 不要用更多布尔值修补状态组合。
- 不要在 Qt 主线程等待 Future、网络请求或线程退出。
- 不要让手动刷新绕过运行时的账号请求调度器。
- 不要持久化当前任务 ID、当前进度、下一次检查时间或后台自动开关。
- 不要通过任务名称、开播时间或按钮文字推断运行所有者。

## 12. 推荐的第一批实现范围

第一批只处理高风险正确性，不做大规模文件拆分：

1. 补齐 P0 特征测试。
2. 修复领奖异常路径。
3. 引入 `RunOwner`，统一所有自动停止分支。
4. 把加载设置改成显式关闭后台自动并等待确认。
5. 为后台检查结果加 generation，防止过期结果覆盖。
6. 增加诊断日志：启动原因、运行所有者、停止原因。

第一批完成后再进入状态机和请求队列阶段。这样即使后续架构重构暂停，当前软件也先得到最关键的稳定性修复。

## 13. 2026-08-01 实施状态

本轮已经完成可在现有运行结构中安全落地的加固层：
